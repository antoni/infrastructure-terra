## What changed

`mountain_tile_backend` no longer owns anything generic. A host is built by three roles, in order:

1. `geerlingguy.docker` 8.0.0: Docker Engine and Compose; `daemon.json` has the `local` log driver, 20 MB x 5 files
   (`inventory/group_vars/tile_backend.yml`).
2. `yourorg.shared_roles.reverse_proxy`: nginx, TLS policy, Let's Encrypt, security headers, real IP, rate-limit zones.
3. `services/mountain_tile_backend`: its own vhost on that proxy, the two containers, release validation, activation,
   rollback, smoke tests, opt-in retention.

`playbooks/tile_backend_host.yml` runs them (tags `docker`, `proxy`, `app`); `playbooks/mountain_tile_backend.yml` runs
only the app role (the local rehearsals use it). `requirements.yml` pins both dependencies; `make deps` installs them.

## Findings worth knowing

- **Upstream keep-alive.** The shared `proxy.conf` sends `Connection: $connection_upgrade` (= `close` for ordinary requests); an
  empty `proxy_set_header Connection ""` in the same location does not override it (both are sent, checked with tcpdump). Through it
  the origin saw about 1,000 new loopback connections per second. The role ships its own forwarding snippet for the vhost.
  If the map in `reverse_proxy` yielded `''` instead of `close` for non-upgrade requests, the snippet could go.
- **The proxy hop's cost could not be measured.** The test VPS varied 3x between identical runs. The reasoning, and what was
  measured instead, is in the role README.
- **Let's Encrypt on `goodsrv.de` names is unreliable**: the shared registered domain hit the 50-certificates-per-week limit twice.
  A real certificate needs a domain of ours.
- `reverse_proxy` worked on Debian 13 although its metadata lists Debian 11/12 and Ubuntu 22/24.
